## What this is

A clean-room reference implementation of a real-world multi-tenant attendance
API. Built around three engineering choices most fresher portfolios don't show:

| Choice | What it proves |
|--------|----------------|
| **DB-per-tenant** with per-request `DbContext` factory | I understand SaaS data isolation |
| **3 distinct ingestion modes** converging on one service | I can design for varied client capabilities |
| **AI-assisted schema inference** as a feature | I use modern AI tooling thoughtfully, not as a crutch |

Domain: institutional biometric attendance (clean-room model of an
education-tech ERP). All data is synthetic, generated by `tools/SeedData`.

## Tech stack

| Layer | Choice | Why |
|-------|--------|-----|
| Runtime | .NET 8 LTS | Modern, supported, fast |
| API | ASP.NET Core minimal APIs | Less ceremony than MVC for an analytics-leaning service |
| ORM | Entity Framework Core 8 | Per-request DbContext, raw-SQL escape hatch when needed |
| Database | SQL Server 2022 | Matches enterprise reality |
| Auth (showcase) | X-Tenant-Id header | Production would layer OAuth on top |
| Logging | Serilog → console | Structured, ready for Datadog / Seq sinks |
| Docs | Swashbuckle + XML comments | Browse at `/swagger` |
| AI | Anthropic Claude Haiku 4.5 | Tiny task (schema inference), fast + cheap |
| Test | xUnit + FluentAssertions + Testcontainers | Real SQL Server in integration tests |
| Container | docker-compose: api + sqlserver | One-command stand-up |

## Quick start

### Run via Docker (recommended, ~2 minutes)

```bash
git clone https://github.com/Yugandhar2807/attendance-analytics-api.git
cd attendance-analytics-api
cp .env.example .env
# Optional: paste your ANTHROPIC_API_KEY into .env to enable /api/v1/ai/*
docker-compose up -d
```

Then open `http://localhost:5080/swagger`.

### Run locally against LocalDB

```powershell
dotnet restore
dotnet build
dotnet run --project src/Attendance.Api
```

API will be at `http://localhost:5080/swagger`.

### Seed synthetic data into one tenant

```powershell
dotnet run --project tools/SeedData -- --users=500 --days=30 `
    --conn="Server=(localdb)\MSSQLLocalDB;Database=AttendanceTenantA;Trusted_Connection=true;TrustServerCertificate=true"
```

## Try the 3 ingestion modes

### Mode 1 — Single REST punch
```bash
curl -X POST http://localhost:5080/api/v1/punches \
  -H "X-Tenant-Id: tenant-a" \
  -H "Content-Type: application/json" \
  -d '{
    "externalRef": "EXT00001",
    "punchAt": "2026-04-15T09:02:00Z",
    "deviceId": "DEV-01",
    "direction": "IN"
  }'
```

### Mode 2 — CSV upload (UI flow)
```bash
curl -X POST http://localhost:5080/api/v1/punches/batch \
  -H "X-Tenant-Id: tenant-a" \
  -F "file=@samples/synthetic-data/tenant-a-punches.csv"
```

### Mode 3 — PowerShell webhook
```powershell
.\samples\powershell-sender\send-punches.ps1 `
    -ApiBase http://localhost:5080 `
    -TenantId tenant-a `
    -CsvPath samples\synthetic-data\tenant-a-punches.csv
```

All 3 modes converge on the same `CoreIngestionService` — same idempotency
guarantees, same error shape, same audit trail.

## AI-assisted schema inference

Onboarding a new tenant who sends data in a different shape? POST a sample, get
back the mapping:

```bash
curl -X POST http://localhost:5080/api/v1/ai/infer-schema \
  -H "X-Tenant-Id: tenant-a" \
  -H "Content-Type: application/json" \
  -d '{
    "csvSample": "CardNo,TimeStamp,DEV,InOut\n1234,2026-04-15 09:02,A1,I"
  }'
```

Response:
```json
{
  "mapping": {
    "externalRefColumn": "CardNo",
    "punchAtColumn": "TimeStamp",
    "deviceIdColumn": "DEV",
    "directionColumn": "InOut"
  },
  "confidence": 0.95,
  "reasoningSummary": "CardNo maps to external_ref (numeric ID, single column); InOut to direction (I/O abbreviation)."
}
```

Requires `ANTHROPIC_API_KEY` in env. Implementation
[`ClaudeSchemaInferenceService.cs`](src/Attendance.Infrastructure/AiAssist/ClaudeSchemaInferenceService.cs).
Read about the workflow in [`docs/ai-assisted-workflow.md`](docs/ai-assisted-workflow.md)
and the actual prompts in [`prompts/`](prompts/).

## API surface

| Method | Route | Purpose | Tenant required |
|--------|-------|---------|-----------------|
| `GET`  | `/health` | Liveness probe | no |
| `GET`  | `/health/ready` | Readiness probe | no |
| `GET`  | `/swagger` | OpenAPI UI | no |
| `POST` | `/api/v1/punches` | Single punch (REST) | yes |
| `POST` | `/api/v1/punches/batch` | CSV upload | yes |
| `POST` | `/api/v1/punches/webhook` | Webhook receiver (PowerShell, etc.) | yes |
| `GET`  | `/api/v1/analytics/absenteeism?from=&to=` | Absenteeism KPI | yes |
| `GET`  | `/api/v1/analytics/punctuality?from=&to=` | On-time KPI | yes |
| `POST` | `/api/v1/ai/infer-schema` | AI schema inference (Claude) | yes |

Full OpenAPI spec at `/swagger`.

## What I learned building this

1. **DB-per-tenant trades cost for safety, and that trade is right for regulated SaaS.** No `WHERE tenant_id =` filter to forget; the DB itself is the boundary. Operational cost is real but operational tooling matters more.
2. **The "AI in your app" pattern is more about prompt + JSON schema than about the model.** Claude Haiku 4.5 was a deliberate choice — Sonnet would be overkill for column-name reasoning.
3. **AI as a pair-programming tool is not the same as AI-in-the-app**, and showing both in one repo (`/api/v1/ai/*` for the former, `prompts/` for the latter) makes the difference legible to reviewers.
4. **Three ingestion modes is one architecture, not three.** The strategy pattern + `IAsyncEnumerable<IncomingPunch>` lets all 3 modes share dedup, validation, and audit. Adding a 4th (SFTP file watcher? gRPC stream?) would be 50 lines.
